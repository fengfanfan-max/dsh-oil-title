# 兼容性说明

## 版本门禁是什么

DSH 0.2.x 的插件管理器在安装后校验插件的 `peerDependencies`，判断是否覆盖当前 `dsh` 版本。不覆盖就整体回滚安装并给出：

```
dsh: installation rejected: Plugin <name>@<ver> is incompatible with dsh <ver>: requirements {...}
```

这不是运行时错误，而是安装期保护。DSH 也提供逃生舱（`dsh plugin allow-version ... --accept-risk`），但那是用户逐版本手工放行，不适合长期使用。

## 本插件的声明

```json
"peerDependencies": {
  "@deepseek-ai/cordis": ">=4.0.2 <5.0.0",
  "@deepseek-ai/dsh-llm": ">=0.1.2-rc.1 <0.3.0",
  "@deepseek-ai/dsh-session": ">=0.1.2-rc.1 <0.3.0",
  "@deepseek-ai/dsh-session-title": ">=0.1.2-rc.1 <0.3.0"
},
"peerDependenciesMeta": { "...": { "optional": true } }
```

选 `<0.3.0` 而不是 `*`：0.3.0 是一次未验证的 API 断代，超过它应当由本仓库重新验证后再放开，而不是静默放行。

## 自动化验证（CI）

`compat.json` 是唯一事实来源：

```json
{
  "packages": ["@deepseek-ai/dsh-session", "@deepseek-ai/dsh-session-title", "@deepseek-ai/dsh-llm"],
  "verifiedDshVersions": ["0.1.2-rc.1", "0.2.1-rc.1", "0.2.1-rc.2"]
}
```

`.github/workflows/ci.yml` 为每个版本起一个 job：

1. 在临时目录安装该版本的三个官方包；
2. 用 TypeScript 编译 `test/compat/probe.ts`；
3. 探针只调用插件实际依赖的接口 —— `sessions.list/get`、`session.snapshotEvents`、`session.requestHeader`、`session.header.cwd`、`sessionTitle.get/rename`、`llm.stream` 及其选项字段。

编译通过即表示这些接口在该版本仍然存在且签名兼容，这就是插件「支持某个 dsh 版本」的证据。

本地执行：

```sh
npm run test:compat                      # 跑 compat.json 里的全部版本
node scripts/compat-matrix.mjs --version 0.2.1-rc.2   # 只跑一个
```

新增版本：把它加进 `compat.json` 的 `verifiedDshVersions`，跑一遍矩阵；`test/compat.test.mjs` 会同时断言 peer 范围覆盖该版本，避免出现「CI 验过但装不上」。

## 每次升级 dsh 后怎么复核

1. `npm test` —— 单元测试 + 范围回归。
2. `npm run test:compat` —— 类型探针矩阵。
3. 真机验证：新会话发一条需求，确认侧边栏出现带一个 emoji 与全角 `｜` 的标题，且对话里没有多出命名消息。
4. 三步都通过后，再把 `<0.3.0` 的上界按实际验证结果调整。
